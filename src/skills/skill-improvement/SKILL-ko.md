# 작업을 마친 뒤 스킬 개선 제안

완료 전 회고에서는 사용자가 처음 요청한 일과 후속 요청을 모두 마치고 검증한다. 최종 보고 직전에 끝낸 작업을 검토한다. 사용자가 회고를 명시적으로 요청하면 그때까지 완료한 작업을 검토한다.

## 다른 작업에도 적용할 수 있는지 판단한다

1. 사용자가 지적한 부분, 후속 요청에서 명확해진 요구사항, 검증 중 드러난 문제를 확인한다. 어떤 판단을 놓쳤고 그 결과로 무슨 일이 있었는지 적는다.
2. 현재 스킬과 관련 프로젝트 지침을 읽는다. 지침이 빠져 있었는지, 필요한 스킬을 찾기 어려웠는지, 이미 분명한 지침을 실행에서 놓쳤는지 확인한다.
3. 이름과 티켓 등 이번 작업의 세부사항을 다른 현실적인 사례로 바꿔 본다. 원인과 필요한 조치가 같고 변경으로 실제 문제를 예방할 가능성이 높을 때만 제안한다. 반복된 근거는 판단에 도움이 된다. 한 번의 사례라도 다른 곳에서 같은 문제가 생기는 원리를 확인했거나 재발할 수 있는 중대한 빈틈을 드러냈다면 제안할 수 있다. 일반적인 범위 추가, 일회성 장애, 특정 환경에서만 생기는 예외는 건너뛴다.

## 가장 좁은 범위에서 해결한다

- 자동 검사로 요구사항을 안정적으로 확인할 수 있으면 lint, hook, 타입, 테스트, 스크립트 검사를 제안한다. 스킬에 이미 지침이 명확하면 같은 규칙을 덧붙이지 않는다. 실제 누락을 잡을 수 있을 때만 검사를 제안한다.
- 프로젝트 관례는 그 프로젝트의 지침이나 검사에 제안한다. 사용자가 앞으로도 적용하겠다고 밝힌 개인 선호는 사용자 지침이나 메모를 제안한다. 각각 해당 범위에 둔다.
- 재사용할 판단 기준이나 절차가 빠졌으면 해당 주제를 담당하는 스킬의 최소 변경을 제안한다. 스킬을 불러오지 못했다면 호출 조건이나 설명을 수정한다. 독립적인 절차가 필요하고 담당 스킬이 없을 때만 새 스킬을 제안한다.

## 개선안을 보고한다

제안할 가치가 있으면 작업 결과 뒤에 개선안을 짧게 덧붙인다. 대상 스킬이나 검사, 이번 작업에서 얻은 근거, 다음에 달라질 행동을 적는다. 사용자가 해당 변경을 이미 요청한 경우는 바로 진행하고, 그 외에는 적용 여부를 묻는다. 해당하는 후보가 없으면 작업 결과로 마친다. 사용자가 회고를 명시적으로 요청한 경우에는 제안이 없는 이유를 짧게 설명한다.

## 승인받은 개선을 적용한다

사용자가 지정한 범위를 따른다. 스킬을 변경할 때는 사용할 수 있는 스킬 작성 지침을 따른다.

hibi-ai 스킬은 `~/.hibi/install.json`이 있으면 스킬의 출처와 설치 대상을 확인한다. 해당 hibi-ai 원본 저장소의 복제본이 없고 사용자가 적용 범위를 지정하지 않은 채 수정을 승인했다면, 현재 에이전트가 사용하는 설치본만 수정하고 그곳에서 검증한다. 로컬 적용에는 저장소 복제가 필요 없다.

설치본의 변경을 검증한 뒤 적용 위치를 알린다. 다른 hibi-ai 사용자에게도 도움이 될 개선이라면 원본 저장소에 PR을 올릴지 묻는다. 사용자가 PR을 요청하면 `pull-request` 스킬을 따른다.
