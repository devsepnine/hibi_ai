# QA 인수인계 문서

지정한 git 범위의 개발 내역을 한 문서로 만든다. 문서는 두 단으로 구성된다.
팀 누구나 읽을 수 있는 변경 요약과, 그대로 실행할 수 있는 QA 체크리스트다.
읽는 사람은 제품은 알지만 코드베이스는 모른다는 전제로 쓴다.

## 왜 이 구성인가

QA가 시간을 잃는 지점은 두 곳이다. 어떤 변경이 눈에 보이는지 모를 때, 그리고
재현 방법을 모를 때다. 변경 전과 후를 비교하고, 체크리스트 항목마다 전제·재현 절차·기대
결과를 붙인다. 외부에서 관찰할 수 없는 내부 변경은 문서에서 제외한다.
확인할 필요가 없는 작업을 별도 목록으로 나열하면 QA가 읽을 분량만 늘어난다.

커밋 근거가 필요하면 문서 끝에 짧게 모은다. 요약·변경표·체크리스트마다
해시를 반복하지 않는다. QA가 코드를 읽지 않아도 문서를 이해할 수 있어야 한다.

## 워크플로우

### 1. 저장소 상태를 확인한 뒤 범위를 확정한다

범위 계산은 무엇이 체크아웃되어 있는지에 좌우되고, 여기서 발생하는 오류는 전부
조용하다. 엉뚱한 커밋을 설명하는 그럴듯한 문서가 나온다. 먼저 세 가지를 확인한다.

```bash
git rev-parse --is-shallow-repository                  # true → 이력이 잘려 있음
git symbolic-ref --short -q HEAD || echo "detached"    # 현재 브랜치, 또는 detached HEAD
git describe --tags --abbrev=0 2>/dev/null || echo "no tags"
```

- **`git describe`는 저장소의 최신 태그가 아니라 HEAD에서 도달 가능한 최신 태그를 반환한다.** 마지막 릴리즈 이전에 분기한 브랜치에서는 더 오래된 태그가 나오고, `<tag>..HEAD` 가 커밋 0개로 잡힐 수 있다. `git tag --sort=-v:refname | head -1` 과 비교해 다르면 어느 쪽을 왜 썼는지 밝힌다. 두 후보 모두 빈 범위로 이어지면 세 번째 태그를 찾을 문제가 아니다. 지금 체크아웃된 브랜치가 뒤처져 있을 가능성이 높으므로, 출력이 나오는 범위를 뒤지지 말고 사용자에게 브랜치가 최신인지 확인을 요청한다. 예를 들면 `git checkout main && git pull`이다.
- **shallow clone**: 태그와 옛 커밋이 아예 없을 수 있어 범위가 실제보다 훨씬 짧아 보인다. 진행 전에 사용자에게 알린다.
- **`git describe` exit 128**, 메시지 "fatal: No names found"는 태그가 하나도 없다는 뜻이다. 에러로 처리하지 말고 아래 무태그 경로로 분기한다.

그다음 범위를 확정한다. 정말 모호할 때만 묻고, 그 외에는 기본값을 쓰고 무엇을
썼는지 밝힌다.

- 사용자가 준 명시적 범위가 최우선이다. `v1.14.0..HEAD`, 브랜치, "지난주"가 그 예다. 상대 표현은 rolling 기준으로 읽는다. "지난주"는 캘린더 주가 아니라 최근 7일이며, 그 해석을 문서에 명시한다.
- 대화에서 방금 완료한 기능이나 티켓이면 확인된 해당 커밋을 사용한다. 전체 릴리즈로 범위를 넓히지 않는다.
- 기본값: `<도달 가능한 최신 태그>..HEAD`.
- 태그가 없으면: 두 후보 구간의 커밋 수를 직접 세어 더 적은 쪽을 쓴다.

```bash
git log --oneline --since='7 days ago' | wc -l   # 후보 A
git log --oneline -20 | wc -l                    # 후보 B
```

- **범위에 커밋이 0개면**: 문서를 만들지 말고 그 사실을 보고한다. 빈 범위로 만든 문서는 "바뀐 게 없다"로 읽히지만 실제로는 "범위가 잘못됐다"는 뜻이다.
- **커밋이 약 30개를 넘으면**: 한 화면 요약과 변경당 한 줄을 동시에 지킬 수 없다. 범위를 좁히도록 제안하거나 커밋 단위가 아니라 기능 단위로 행을 묶고, 둘 중 무엇을 했는지 밝힌다. diffstat 단계는 `git log --no-merges --stat=80,40` 을 쓰거나 큰 커밋만 표본으로 본다. 모든 stat 블록을 컨텍스트에 쏟아붓지 않는다.

### 2. 제목만 보지 말고 이력을 읽는다

```bash
git log --no-merges --date=short --pretty='%h %ad %s' <range>
git log --no-merges --stat <range>     # 어떤 파일이 움직였나
git show <sha> -- <path>               # 제목만으로 부족할 때
```

커밋 제목은 생략으로 거짓말한다. `fix: guard empty input` 은 사용자가 무엇을
다르게 보는지 아무것도 말해주지 않는다. 확신을 갖고 분류할 수 없는 변경은 diff를
직접 읽는다. 추측으로 채운 체크리스트는 짧은 체크리스트보다 나쁘다. QA가 어느
항목을 믿어야 할지 판단할 수 없기 때문이다.

### 3. 각 변경을 "사용자가 겪는 차이"로 번역한다

커밋마다 질문 하나에 답한다. **제품을 쓰는 사람이 이제 무엇을 다르게 겪는가?**
제품 용어로 한 문장.

| 커밋 | 약한 서술, 개발자 언어 | 쓸 수 있는 서술 |
|---|---|---|
| `fix: resolve CLI program via PATHEXT` | "resolve_cli_program이 PATH를 직접 탐색한다" | "Windows에서 npm으로 설치한 MCP 서버가 목록에 표시된다. 이전에는 목록이 비어 있었다." |

정직한 답이 "보이는 변화 없음"이면 QA 문서에서 제외한다.
리팩터링과 테스트 유지보수 내역은 개발 기록에 남긴다.

단 하나의 예외가 이 규칙보다 우선한다. 인증·권한·데이터 무결성 관련 변경은
정상 흐름에서 아무 차이가 안 보이는 것이 **설계 의도**다. 이런 변경은
negative-path 항목으로 체크리스트에 넣는다. 예를 들면 "만료된 토큰으로 요청하면 거부된다"이다.
검증해야 할 대상이 "더 이상 일어나지 않는 일"이기 때문이다.

### 4. API 변경을 제품의 동작과 연결한다

이번 작업에서 API 계약을 바꾸거나 변경된 계약을 사용한다면 변경 전후 비교 다음에
**API 변경사항**을 넣는다. 영어 제목은 **API changes**다.
확인된 요청 경로를 적고, 변경 항목·변경 내용·사용되는 화면이나 동작을 표로 정리한다.
이 섹션에서는 정확한 API 필드명을 사용하되, QA가 응답과 화면을 연결할 수 있도록
쉬운 설명을 붙인다. 예를 들어 새로 받은 보상 수량과 개당 금액을 곱해 보너스 선택
목록의 금액으로 표시한다고 설명한다. API 문서나 관련 백엔드 티켓도 연결한다.
변경 예정인 계약과 실제 응답에서 확인한 내용을 구분한다. 이전 필드를 추측하거나
응답을 사용하는 화면 수정만으로 API 배포가 완료됐다고 쓰지 않는다.
관련 API 변경이 없으면 섹션을 생략한다. 전체 스키마를 붙이거나 QA 체크리스트에
코드 검토를 요구하지 않는다.

### 5. 실행 가능한 체크리스트로 쓴다

체크리스트는 개발자가 QA에게 확인을 요청하는 항목이며 릴리즈 승인 기준이 아니다.
항목마다 **전제**, **재현 절차**, **기대 결과**를 사용한다.
영어는 **Setup**, **Reproduction steps**, **Expected result**로 쓴다.
전제에는 재현에 필요한 계정·데이터·환경만 적고 동작에는 번호를 붙인다.
필수·보조·must-pass·릴리즈 차단 같은 우선순위 표시는 넣지 않는다. 커밋 순서가 아니라 사용자
흐름 순으로 배열한다. 테스터는 git 이력이 아니라 화면을 따라 움직인다.

### 6. 회귀 위험 구간을 지목한다

다시 확인할 기존 기능과 유지되어야 할 동작을 구체적으로 적는다.
의존성 구조 대신 사용자가 겪을 영향을 설명한다. 예를 들어 기존 보너스의
이름과 금액이 이전과 동일하게 표시되는지 확인해 달라고 쓴다.

### 7. 자동 검증 결과를 제품의 동작으로 설명한다

확인한 동작과 실제 결과를 먼저 쓰고 테스트 개수나 커버리지는 뒤에 짧게 덧붙인다.
테스트용 응답을 사용했는지 실제 서비스에 연결했는지 밝히고, 해당 기능의 커버리지와
전체 앱의 커버리지를 구분한다. 남은 수동 확인과 연동 검증도 명시한다.
로컬 테스트 통과를 배포 완료·전체 E2E 검증·운영 준비 완료로 표현하지 않는다.

### 8. 판단할 수 없었던 것을 드러낸다

모르는 것은 개발자에게 물을 질문과 함께 "확인 필요"에 넣는다. 그럴듯한 추측으로
빈칸을 메우지 않는다. 기대 결과가 틀리면 QA는 존재하지 않는 버그를 쫓게 되고,
그 비용이 "모른다"고 적는 비용보다 훨씬 크다.

물어볼 대상까지 적는다. `git log --format='%an' -1 <sha>` 로 그 질문이 나온
커밋의 작성자를 알 수 있어, 여러 사람이 손댄 범위에서 QA가 누구에게 물어야
할지 헤매지 않는다.

### 9. 출력 위치를 선택받는다

먼저 어떤 요청인지 읽는다. 결과를 공유하거나 보관해야 한다는 신호가 있으면 문서 생성 요청이다. 팀 전체가
볼 것, 나중에 다시 참조할 것, 다른 조직에 넘길 것이 그 신호다.
지금 당장 답이 필요한 단발성 물음이면 질문이다.

문서 생성 요청이면 사용자가 미리 지정하지 않았다면 어디에 남길지 묻는다. 질문이면
"내일 릴리즈인데 QA가 뭘 봐야 하나?" 같은 경우 대화에서 바로 답하고 저장할지 제안한다.
지금 답이 필요한 사람에게 파일 경로를 되묻는 것은 잡음이다.

- 저장소에 마크다운 파일로 저장. 기본 경로는 `docs/handoff/<YYYY-MM-DD>-<range-slug>.md`. 범위 문자열을 먼저 슬래시·공백을 제거해 slug로 바꾼다. 예를 들면 `feature/foo..HEAD` → `feature-foo-HEAD`이다. 그러지 않으면 브랜치명이 조용히 하위 디렉터리를 만든다.
- 대화창에만 출력. Slack·Confluence에 붙여 쓰는 용도
- Confluence 게시. Atlassian MCP를 쓰며 space와 parent page가 필요하다
- 요청한 Jira 디스크립션 수정. 제목·담당자·기존 본문을 먼저 읽는다. "내 티켓"이면 상위 에픽으로 단정하지 말고 사용자의 구현 티켓을 찾는다. 대상이 여전히 모호할 때만 묻는다. 무관한 기존 내용은 보존하고 저장된 본문을 다시 읽어 확인한다.

저장소에 파일을 쓰는 것도 content 변경이므로, `CLAUDE.md` 의 post-work review
게이트가 다른 변경과 동일하게 적용된다.

## 문서 템플릿

`assets/handoff-template.md` 를 골격으로 쓴다. 섹션 순서는 유지한다. QA는
위에서 아래로 읽고 필요한 정보를 얻은 지점에서 멈춘다.
한글 섹션 이름은 전체 요약, 기존과 달라진 변경사항, API 변경사항, QA 체크리스트,
회귀 주의 영역, 자동 검증 결과, 용어 설명, 개발자 확인 사항으로 쓴다. API 변경사항은 해당할 때만 넣는다.
배포 전제를 기본 항목으로 넣지 않는다. 재현에 필요한 조건은 해당 체크리스트의
전제에, 답변이 필요한 내용은 개발자 확인 사항에 넣는다.

## 작성 규칙

- **두괄식**: 모든 불릿은 결론부터, 상세는 뒤에 둔다. `coding-standards` 와 동일한 규칙이다.
- **제품 용어**: 요약과 체크리스트에 파일명·함수명·타입명을 쓰지 않는다. 기술 용어가 불가피하면 용어 사전에 정의한다. 예외: 저장소 자체가 제품인 경우, 즉 툴링·설정·스킬·템플릿 저장소에는 skill·command·설정 이름이 곧 제품 용어다. 정확한 이름으로 쓰고, 환경 전제조건 대신 읽는 사람에게 필요한 설치·싱크 상태를 적는다.
- **변경 하나에 한 줄**: 커밋 세 개를 "여러 개선 사항"으로 묶지 않는다.
- **얼버무리지 않기**: "확인 필요"는 정직하고, "아마 문제 없을 것"은 아니다.
- **요약은 한 화면**: 상세는 요약이 아니라 체크리스트에 넣는다.
- **변경 전후 비교**: 관찰 가능한 변경마다 이전과 이후의 동작을 비교한다. 내부 구현 설명은 비교표에서 제외한다.
- **용어는 명확하고 명료하게**: 이 문서를 이해하는 데 필요한 용어만 고른다. 한 용어당 한 문장으로 일상 언어로 설명한다. 비슷한 용어는 차이가 드러나게 쓰고 다른 전문용어로 풀어 설명하지 않는다. 코드명과 무관한 내부 구현 용어는 제외한다.
- **개발자 확인 사항은 구체적으로**: 아직 답변이 필요한 질문, 답할 사람, 해당 답변이 필요한 QA 항목을 적는다. 일반적인 배포 점검표를 추가하지 않는다.
