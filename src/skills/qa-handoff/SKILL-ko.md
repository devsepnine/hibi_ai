# QA 인수인계 문서

지정한 git 범위의 개발 내역을 한 문서로 만든다. 문서는 두 단으로 구성된다 —
팀 누구나 읽을 수 있는 변경 요약, 그리고 그대로 실행할 수 있는 QA 체크리스트.
읽는 사람은 제품은 알지만 코드베이스는 모른다는 전제로 쓴다.

## 왜 이 구성인가

QA가 시간을 잃는 지점은 두 곳이다. 어떤 변경이 눈에 보이는지 모를 때, 그리고
재현 방법을 모를 때다. 그래서 문서는 **사용자 눈에 보이는 변경**과 **확인이
필요 없는 내부 변경**을 분리하고, 체크리스트 항목마다 전제조건·절차·기대
결과를 붙인다. 외부에서 관찰할 수 없는 변경을 체크리스트에 넣으면 테스터의
반나절이 그냥 날아간다.

추적성은 반대 방향으로도 필요하다. 항목마다 커밋을 인용해 두면 개발자가
"이 항목이 왜 있나"를 범위 전체를 다시 읽지 않고 답할 수 있다.

## 워크플로우

### 1. 저장소 상태를 확인한 뒤 범위를 확정한다

범위 계산은 무엇이 체크아웃되어 있는지에 좌우되고, 여기서 발생하는 오류는 전부
조용하다 — 엉뚱한 커밋을 설명하는 그럴듯한 문서가 나온다. 먼저 세 가지를 확인한다.

```bash
git rev-parse --is-shallow-repository                  # true → 이력이 잘려 있음
git symbolic-ref --short -q HEAD || echo "detached"    # 현재 브랜치, 또는 detached HEAD
git describe --tags --abbrev=0 2>/dev/null || echo "no tags"
```

- **`git describe`는 저장소의 최신 태그가 아니라 HEAD에서 도달 가능한 최신 태그를 반환한다.** 마지막 릴리즈 이전에 분기한 브랜치에서는 더 오래된 태그가 나오고, `<tag>..HEAD` 가 커밋 0개로 잡힐 수 있다. `git tag --sort=-v:refname | head -1` 과 비교해 다르면 어느 쪽을 왜 썼는지 밝힌다. 두 후보 모두 빈 범위로 이어지면 세 번째 태그를 찾을 문제가 아니다 — 지금 체크아웃된 브랜치가 뒤처져 있을 가능성이 높으므로, 출력이 나오는 범위를 뒤지지 말고 사용자에게 브랜치가 최신인지 확인을 요청한다(`git checkout main && git pull`).
- **shallow clone**: 태그와 옛 커밋이 아예 없을 수 있어 범위가 실제보다 훨씬 짧아 보인다. 진행 전에 사용자에게 알린다.
- **`git describe` exit 128** ("fatal: No names found")은 태그가 하나도 없다는 뜻이다. 에러로 처리하지 말고 아래 무태그 경로로 분기한다.

그다음 범위를 확정한다. 정말 모호할 때만 묻고, 그 외에는 기본값을 쓰고 무엇을
썼는지 밝힌다.

- 사용자가 준 명시적 범위(`v1.14.0..HEAD`, 브랜치, "지난주")가 최우선. 상대 표현은 rolling 기준으로 읽는다 — "지난주"는 캘린더 주가 아니라 최근 7일이며, 그 해석을 문서에 명시한다.
- 기본값: `<도달 가능한 최신 태그>..HEAD`.
- 태그가 없으면: 두 후보 구간의 커밋 수를 직접 세어 더 적은 쪽을 쓴다.

```bash
git log --oneline --since='7 days ago' | wc -l   # 후보 A
git log --oneline -20 | wc -l                    # 후보 B
```

- **범위에 커밋이 0개면**: 문서를 만들지 말고 그 사실을 보고한다. 빈 범위로 만든 문서는 "바뀐 게 없다"로 읽히지만 실제로는 "범위가 잘못됐다"는 뜻이다.
- **커밋이 약 30개를 넘으면**: 한 화면 요약과 변경당 한 줄을 동시에 지킬 수 없다. 범위를 좁히도록 제안하거나 커밋 단위가 아니라 기능 단위로 행을 묶는다 — 둘 중 무엇을 했는지 밝힌다. diffstat 단계는 `git log --no-merges --stat=80,40` 을 쓰거나 큰 커밋만 표본으로 본다 — 모든 stat 블록을 컨텍스트에 쏟아붓지 않는다.

### 2. 제목만 보지 말고 이력을 읽는다

```bash
git log --no-merges --date=short --pretty='%h %ad %s' <range>
git log --no-merges --stat <range>     # 어떤 파일이 움직였나
git show <sha> -- <path>               # 제목만으로 부족할 때
```

커밋 제목은 생략으로 거짓말한다 — `fix: guard empty input` 은 사용자가 무엇을
다르게 보는지 아무것도 말해주지 않는다. 확신을 갖고 분류할 수 없는 변경은 diff를
직접 읽는다. 추측으로 채운 체크리스트는 짧은 체크리스트보다 나쁘다. QA가 어느
항목을 믿어야 할지 판단할 수 없기 때문이다.

### 3. 각 변경을 "사용자가 겪는 차이"로 번역한다

커밋마다 질문 하나에 답한다. **제품을 쓰는 사람이 이제 무엇을 다르게 겪는가?**
제품 용어로 한 문장.

| 커밋 | 약한 서술 (개발자 언어) | 쓸 수 있는 서술 |
|---|---|---|
| `fix: resolve CLI program via PATHEXT` | "resolve_cli_program이 PATH를 직접 탐색한다" | "Windows에서 npm으로 설치한 MCP 서버가 목록에 표시된다. 이전에는 목록이 비어 있었다." |

정직한 답이 "보이는 변화 없음"이면 내부 변경이다. 왜 보이지 않는지 한 구절을
붙여 내부 변경 목록에 넣는다.

단 하나의 예외가 이 규칙보다 우선한다. 인증·권한·데이터 무결성 관련 변경은
정상 흐름에서 아무 차이가 안 보이는 것이 **설계 의도**다. 이런 변경은
negative-path 항목("만료된 토큰으로 요청하면 거부된다")으로 체크리스트에 넣는다.
검증해야 할 대상이 "더 이상 일어나지 않는 일"이기 때문이다.

### 4. 실행 가능한 체크리스트로 쓴다

항목마다 전제조건(계정·데이터·환경) → 번호 붙인 절차 → 기대 결과를 갖춘다.
우선순위를 표시한다 — 필수(릴리즈 차단) 또는 보조. 커밋 순서가 아니라 사용자
흐름 순으로 배열한다. 테스터는 git 이력이 아니라 화면을 따라 움직인다.

### 5. 회귀 위험 구간을 지목한다

공용 모듈, 설정 파일, 마이그레이션, 플랫폼별 경로를 건드린 변경은 이번에 손대지
않은 기능까지 위험에 넣는다. 어떤 기능이 왜 위험한지 밝혀서, 한정된 회귀
테스트 시간이 변경이 실제로 닿는 곳에 쓰이게 한다.

### 6. 판단할 수 없었던 것을 드러낸다

모르는 것은 개발자에게 물을 질문과 함께 "확인 필요"에 넣는다. 그럴듯한 추측으로
빈칸을 메우지 않는다. 기대 결과가 틀리면 QA는 존재하지 않는 버그를 쫓게 되고,
그 비용이 "모른다"고 적는 비용보다 훨씬 크다.

물어볼 대상까지 적는다. `git log --format='%an' -1 <sha>` 로 그 질문이 나온
커밋의 작성자를 알 수 있어, 여러 사람이 손댄 범위에서 QA가 누구에게 물어야
할지 헤매지 않는다.

### 7. 출력 위치를 선택받는다

먼저 어떤 요청인지 읽는다. 결과를 공유하거나 보관해야 한다는 신호 — 팀 전체가
볼 것, 나중에 다시 참조할 것, 다른 조직에 넘길 것 — 가 있으면 문서 생성 요청이다.
지금 당장 답이 필요한 단발성 물음이면 질문이다.

문서 생성 요청이면 사용자가 미리 지정하지 않았다면 어디에 남길지 묻는다. 질문이면
— "내일 릴리즈인데 QA가 뭘 봐야 하나?" — 대화에서 바로 답하고 저장할지 제안한다.
지금 답이 필요한 사람에게 파일 경로를 되묻는 것은 잡음이다.

- 저장소에 마크다운 파일로 저장 — 기본 경로 `docs/handoff/<YYYY-MM-DD>-<range-slug>.md`. 범위 문자열을 먼저 slug로 바꾼다(슬래시·공백 제거: `feature/foo..HEAD` → `feature-foo-HEAD`). 그러지 않으면 브랜치명이 조용히 하위 디렉터리를 만든다.
- 대화창에만 출력 — Slack·Confluence에 붙여 쓰는 용도
- Confluence 게시 (Atlassian MCP; space와 parent page 필요)

저장소에 파일을 쓰는 것도 content 변경이므로, `CLAUDE.md` 의 post-work review
게이트가 다른 변경과 동일하게 적용된다.

## 문서 템플릿

`assets/handoff-template.md` 를 골격으로 쓴다. 섹션 순서는 유지한다 — QA는
위에서 아래로 읽고 필요한 정보를 얻은 지점에서 멈춘다.

## 작성 규칙

- **두괄식** — 모든 불릿은 결론부터, 상세는 뒤에 (`coding-standards` 와 동일 규칙).
- **제품 용어** — 요약과 체크리스트에 파일명·함수명·타입명을 쓰지 않는다. 기술 용어가 불가피하면 용어 사전에 정의한다. 예외: 저장소 자체가 제품인 경우(툴링·설정·스킬·템플릿 저장소)에는 skill·command·설정 이름이 곧 제품 용어다 — 정확한 이름으로 쓰고, 환경 전제조건 대신 읽는 사람에게 필요한 설치·싱크 상태를 적는다.
- **변경 하나에 한 줄** — 커밋 세 개를 "여러 개선 사항"으로 묶지 않는다.
- **얼버무리지 않기** — "확인 필요"는 정직하고, "아마 문제 없을 것"은 아니다.
- **요약은 한 화면** — 상세는 요약이 아니라 체크리스트에 넣는다.
