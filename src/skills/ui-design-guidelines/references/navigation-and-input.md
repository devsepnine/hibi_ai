# Navigation and input

## Move between a collection and its items

When people compare several records, keep the list and selected detail visible together if both remain readable. When only one fits, open detail as a separate view with a clear return path. Size this transition using actual content, including enlarged text. Carry the selected record across the change in width.

For example, open a message halfway down a filtered inbox. Returning should reveal the same query and list position. If the message was removed, choose a nearby remaining row or show the filtered empty state. A keyboard user needs a reachable focus target in either case.

Source examples include *KDE Human Interface Guidelines*, 2021, “Master Detail”, and *Material Design*, 2018, “Component behavior”.

## Make the action reachable with the available input

- **Touch.** A swipe can accelerate a frequent row action. Give that action a visible entry such as a labeled command in the row menu. Check the hit area near neighboring actions with the target platform's conventions.
- **Keyboard.** Follow focus through the actual task, including entry to and exit from a dialog. If arranging items requires dragging, provide an equivalent operation such as moving the selected item up or down where ordering is supported.
- **Directional remote.** Start with the buttons on the target remote. On a remote with arrows, Select, and Back, use arrows to move visible focus, Select to open the focused item, and Back to return to it. Trace focus across a row boundary. Browsing a channel guide should leave the playing channel identifiable and keep playback running while focus moves.

The input examples draw on *iOS Human Interface Guidelines*, 2014, “Users Know the Standard Gestures”, *GNOME Human Interface Guidelines*, “Keyboard Interaction”, and *Samsung Smart TV Design Guides*, 2022, “Input Methods”. Choose the checks for the devices the product supports.
