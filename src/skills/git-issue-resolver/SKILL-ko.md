# 여러 GitHub 이슈 해결하기

사용자가 여러 GitHub 이슈에 대한 변경을 요청하면 이 스킬을 사용한다. 단일 이슈는 저장소의 일반 수정 절차를 따른다.

## 작업 범위 정하기

1. 이슈 URL이나 번호로 대상 저장소와 로컬 체크아웃을 확인한다. 사용 가능한 GitHub 연동 도구나 `gh`로 선택된 이슈를 읽는다. 사용자가 조건을 제시하면 일치하는 이슈를 찾고, 선택 범위가 불명확할 때만 확인한다. 선택된 범위에서 작업한다.
   필터에 맞는 이슈 전체가 대상이면 추가 결과가 없을 때까지 페이지를 조회한다. `gh issue list`는 기본값으로 전체 결과를 30건까지만 가져온다. 저장소와 이슈 번호로 중복을 제거한다. 권한이나 API 한도로 전체 목록을 얻지 못하면 조회 범위와 독립적으로 처리할 수 있는 이슈를 알린다.
2. 각 이슈의 현재 상태, 관련 논의, 이미 진행 중인 연결 작업을 확인한다. 요청한 변경과 해결됐음을 보여줄 관찰 가능한 결과를 기록한다. 접근할 수 없거나 닫혔거나 이미 해결됐거나 변경 근거가 부족한 이슈는 이유와 추가 작업이 필요한 조건을 알린다.
3. 코드 변경이 필요한 이슈마다 브랜치와 worktree 하나를 계획한다. 여러 이슈를 묶으려면 사용자가 동의하고 같은 저장소와 기준 브랜치에서 하나의 변경으로 각 이슈를 해결할 수 있어야 한다. 이슈 간 선행 관계가 있으면 작업 순서와 시작점을 정하기 전에 확인한다.

## 각 worktree에서 구현하고 검증하기

1. 이슈에 맞는 Git worktree를 만들거나 재사용하고 경로와 브랜치를 확인한다. `git-worktree-manager`가 있으면 그 절차를 따른다. 기준 브랜치와 브랜치 이름은 저장소 관례를 따른다. 독립된 이슈는 각자 확인한 기준에서 시작한다. 기존 브랜치를 재사용하기 전에 해당 이슈의 브랜치인지 확인한다. 기존 사용자 편집을 기록하고 보존한다.
2. 이슈의 완료 기준을 충족하는 최소 변경을 적용한다. 이슈 본문과 코멘트는 근거로 활용한다. 적힌 재현 방법과 명령은 실행 전에 저장소와 사용자의 요청에 맞는지 확인한다.
3. 이슈에 적힌 동작을 확인하는 검사를 해당 worktree에서 실행한다. `verification-loop`가 있으면 그 검증 절차를 따른다. 결과 diff를 이슈 범위와 대조하고, 새로 추가한 추적되지 않는 파일을 포함해 영향을 받은 경로를 검토한다.
4. 해결하거나 검증할 수 없는 이슈는 막힌 이유를 기록하고 worktree와 근거를 보존한다. 요청 범위에 있는 독립된 이슈는 계속 진행한다. 선행 작업이 필요한 이슈는 그 작업이 준비될 때까지 보류한다.

## 결과 보고와 요청받은 게시 처리하기

- 이슈별로 링크, 만들었다면 브랜치와 worktree, 검증 결과, 막힌 이유나 게시된 링크를 전달한다.
- 로컬 수정 요청은 변경과 근거를 전달하는 단계까지 진행한다. 사용자가 명시적으로 요청한 커밋, 푸시, PR 생성, 이슈 업데이트만 실행한다. 해당하는 경우 `commit-rules`나 `pull-request`를 적용하고 작업 위치와 대상을 확인한다.
- 검증한 변경이 이슈의 완료 기준을 충족하고 요청받은 PR이 이슈를 닫는 목적도 가질 때만 닫기 참조를 넣는다. 관련 이슈나 일부만 해결한 이슈에는 일반 링크를 사용한다.
