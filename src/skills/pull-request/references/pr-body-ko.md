# 기본 PR 본문과 리뷰 체크리스트

## 이 템플릿이 적용되는 경우

폴백일 때만이다. 저장소가 자체 PR 템플릿을 갖고 있으면 예외 없이 그것이 우선한다 —
그 섹션들은 메인테이너가 고른 것이고, 그들이 정의한 필드를 찾는 리뷰어는 그것을 찾을 수
있어야 한다. `SKILL.md` §1의 탐색이 아무것도 찾지 못했을 때만 아래를 쓴다.

변경이 건드리지 않은 섹션은 지운다. "N/A" 행으로 채워진 템플릿은 리뷰어가 실제로 봐야
할 두 섹션을 묻어버린다.

## 템플릿

```markdown
#### Type
> 커밋 type과 일치하는 하나: feat / fix / refactor / style / docs / test / chore

#### Background
> 이 PR이 무엇을 하고 왜 하는지. 이슈나 티켓이 있으면 링크한다.

#### Changes
> 주요 변경. 자명하지 않은 부분에는 리뷰어 노트를 붙인다.

**Major files:** `path/file.ext` — 요약

**Compatibility:** 없음 / breaking API (무엇이 깨지고 누가 마이그레이션하는지) / 스키마 마이그레이션 / 데이터 마이그레이션

#### Testing
**Automated:** 어떤 스위트가 이것을 덮는지 — 새 코드에는 새 테스트, 버그 수정에는 회귀 테스트
**Manual:** 손으로 무엇을 어디서 확인했는지
**Performance:** 영향 없음 / 개선 / 저하 (사유)

#### Screenshots
> UI 변경만. Before / after.

#### Links
> 이슈나 티켓, 디자인 문서, 관련 PR. 없으면 행을 지운다.

#### Checklist
- [ ] 셀프 리뷰 완료
- [ ] 커밋이 `commit-rules` 를 따름
- [ ] 디버그 코드나 남은 로깅 없음
- [ ] 시크릿이나 민감 데이터 없음
- [ ] 문서 갱신 · 의존성 변경 시 lockfile · breaking이면 CHANGELOG
```

## 리뷰어 체크리스트

순서가 중요하다 — 앞의 둘이 싸고 가장 많이 잡아내며, 방법은 `SKILL.md` §5에 있다.

- [ ] **본문이 diff와 맞는다** — 모든 주장이 hunk로 대응되고, 자명하지 않은 모든 hunk가 본문에 등장한다
- [ ] **필요성** — 각 hunk가 명시된 목적에 기여한다. 죽은 코드, 투기적 추상화, 이미 있는 것의 재구현, 목적과 무관한 것이 없다
- [ ] **기능성** — 명시된 요구사항을 충족하고, PR이 그 요구사항이 무엇인지 밝히고 있다
- [ ] **정확성** — happy path만이 아니라 엣지 케이스, 에러 경로, 동시 접근
- [ ] **코드 품질** — 가독성, 유지보수성, 주변 코드와의 일관성
- [ ] **설계** — 적절한 아키텍처, 정당화된 결합 (깊이는 `dependency-design`)
- [ ] **보안** — 인젝션 없음, 시크릿 유출 없음, authn/authz 유지 (깊이는 `security-review`)
- [ ] **성능** — 중요한 경로에 회귀 없음
- [ ] **테스팅** — 티어에 맞는 커버리지, 버그 수정에는 회귀 테스트가 붙어 있다
- [ ] **문서** — 동작이나 API가 변경된 곳마다 갱신

## 작성자 체크리스트

- [ ] 남에게 부탁하기 전에 diff를 직접 셀프 리뷰
- [ ] 본문을 브랜치명이나 티켓이 아니라 diff에서 썼다 (`SKILL.md` §2)
- [ ] 컨텍스트 제공 — 무엇만이 아닌 왜. 복원할 수 없는 이유는 지어내지 않고 묻는다
- [ ] 모든 코멘트에 답하고, 어느 분류였고 어디로 갔는지 밝힌다 (`SKILL.md` §6)
- [ ] 리뷰 요청 전에 CI 통과

## 언어

- 기술 용어는 영어로 둔다 (API, database, migration, refactoring).
- 저장소의 기존 PR 언어를 따르고, 아무 단서가 없으면 영어를 기본으로 한다.
- 예: "Add caching logic to improve API response speed"
