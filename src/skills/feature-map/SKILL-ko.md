# 기능맵

`docs/FEATURES.md` 를 만든다. 사용자나 팀원이 **말하는 방식**, 예를 들어 "사이드바에
뭐가 잘 안돼요"나 "입금 문구가 잘 입력이 안돼요"를 받아서, 코드베이스를
먼저 뒤지지 않고도 AI가 그 기능을 구현한 파일에 바로 도달하게 하는 조회표다.

## 왜 이 구성인가

제보는 제품 용어로 들어온다. 화면 어디였는지, 라벨에 뭐라고 적혀 있었는지,
무엇을 하려던 참이었는지. 반면 코드는 모듈 단위로 나뉘어 있다. 이 간극에서
AI는 처음 열 번의 도구 호출을 날린다. "sidebar"로 grep해서 마흔 개가 나오고,
엉뚱한 것부터 읽는다. 기능맵은 사람이 기능을 묘사하는 방식 그대로 색인을 만들어
이 간극을 메운다. **화면 위치, 사용자가 쓰는 단어, 화면에 보이는 실제 문구**.

코드맵, 즉 `doc-updater`가 관리하며 `docs/CODEMAPS/`에 있는 문서와 다른 점이 바로 이것이다. 코드맵은
"코드가 어떻게 구성되어 있나"에 답하고, 기능맵은 "이 제보는 어디에 떨어지나"에
답한다. 둘은 서로 링크하되 한쪽 내용을 다른 쪽에 복사하지 않는다.

읽는 쪽은 모호한 제보가 올 때마다 이 문서를 로드하는 AI다. 그러니 모든 줄이
토큰 값을 해야 한다. 산문이 아니라 경로와 문자열로 쓴다.

## 워크플로우

### 1. 사전 점검: 신규 작성인가 갱신인가

```bash
test -f docs/FEATURES.md && grep -m1 -E '^(Verified at|검증 시점)' docs/FEATURES.md
git rev-parse --short HEAD
find . -path ./node_modules -prune -o -iname 'FEATURES*.md' -print
```

- **`docs/` 밖에 다른 `FEATURES.md`가 있음**: 로드맵이나 홍보용 목록 같은 다른 문서다.
  건드리지 말고, 나중에 누가 둘을 합치지 않도록 헤더의 `참고` 줄에 서로 다른 문서라고 적는다.
- **맵이 없음**: 2단계부터 6단계까지 전체 작성.
- **맵이 있음**: 갱신 모드. [갱신 모드](#갱신-모드) 참고.

사용자가 든 "사이드바", "입금 문구" 같은 예시는 제보의 종류를 보여주는 것이지 기능
목록이 아니다. 제품에 그런 기능이 없으면 보고에서 그렇다고 말한다. 억지로 맞추려고
관계없는 기능에 그 단어를 붙이지 않는다.

### 2. 기능은 바깥에서 안으로 찾는다

디렉터리 트리가 아니라 사용자가 보거나 호출할 수 있는 것에서 시작한다. 트리는
개발자가 일을 나눈 방식이고, 그건 정확히 사용자가 모르는 어휘다.

| 표면 | 주로 있는 곳 |
|---|---|
| 라우트 / 화면 | 라우터 설정, `app/`·`pages/` 디렉터리, 내비게이션 스택 |
| 상주 영역: 사이드바, 헤더, 탭바, 모달 | 레이아웃 컴포넌트, shell/frame 파일 |
| 메뉴와 내비 항목 | 내비 설정 배열, 메뉴 정의 |
| 보이는 문구 | i18n 리소스 파일 `locales/`, `*.json`, `*.po`, `*.arb`, `strings.xml`, JSX에 하드코딩된 텍스트 |
| 에러와 토스트 | 에러 메시지 상수, toast/notification 호출부 |
| CLI / API 제품 | 커맨드 정의, 플래그 파서, 라우트 핸들러, 에러 코드 |

기능 하나 = 사용자가 한 덩어리로 부르는 것, 예: "입금", "사이드바 즐겨찾기",
"로그인". 두 부분이 따로 고장 나고 사용자도 다르게 부르면 나누고, 사용자가
둘을 구별하지 않으면 합친다.

### 3. 기능마다 데이터까지 따라 내려간다

기능마다 코드를 읽어 실제 호출 체인을 따라간다. UI 컴포넌트 → 이벤트 핸들러 /
상태 스토어 → API 클라이언트 → 서버 핸들러 → 저장소. 실제로 있는 단계만 적는다.
클라이언트 전용 앱은 브라우저 저장소에서 끝나고, CLI에는 UI 단계가 없을 수 있다.
어떤 단계가 모든 기능에 없으면 항목마다 빈 줄을 남기지 말고 헤더의 `전제` 줄에
한 번만 적는다. 예: "서버 없음, 상태는 모두 클라이언트". 체인이 HTTP
클라이언트나 ORM 베이스 같은 공용 인프라로 들어가는 지점에서 멈추고, 그 공용 의존은 모든 기능에
나열하지 말고 "공유 의존"으로 적는다.

추적이 가장 자주 덜 끝나는 곳은 영속 상태다. 쓰는 쪽과 읽는 쪽을 **둘 다**
적고, 앱이 마운트되기 전에 그 상태를 건드리는 부트스트랩 지점도 전부 적는다. 예를 들어
`index.html` / `app.html` 의 인라인 스크립트, 여러 컴포넌트에서 호출되는
`init()`. 같은 키나 상수가 두 곳에 정의되어 있으면 함정 후보다. 두 사본은 언젠가
어긋난다.

적는 경로와 심볼은 전부 이번 실행에서 확인한 것이어야 한다: 파일을 열었거나,
grep으로 심볼을 찾아 앞뒤 맥락까지 읽었거나.

### 4. 어휘를 수집한다

맵이 작동하게 만드는 핵심 단계다. 기능마다 네 종류의 단어를 모으고 서로
섞지 않는다. 조회할 때 쓰임새가 다르기 때문이다.

- **실제 UI 문구**: 배포된 그대로의 라벨, 버튼, placeholder, 에러 문구를 큰따옴표로
  감싸 적고, 코드가 그 문구를 찾는 식별자를 붙인다. 키 기반 i18n이면 키,
  예를 들어 `deposit.memo.placeholder`, 원문을 키로 쓰는 Lingui나 gettext 같은 라이브러리면
  원문 `msgid`. grep 앵커이므로 글자 그대로 복사한다. 절대 바꿔 쓰지 않는다.
  번역 항목이 없는 하드코딩 문구는 `(번역 없음)` 으로 표시한다. 값이 끼워 들어가는
  문구는 컴파일된 카탈로그 형태인 `Step {0}/{1}`이 아니라 소스 코드에 있는 형태인
  `Step ${index + 1}/${total}`로 적는다. 카탈로그 형태는 locale 파일에서만 grep된다.
  사용자가 번역된 화면을 본다면 실제로 읽은 번역도 붙인다. 예를 들어 `"Format" · ko "포맷"`이다.
  제보자는 소스가 아니라 화면을 인용한다. `"` 가 들어간 문구는 따옴표로 감쌀 수
  없으므로, 따옴표가 없는 가장 긴 구간을 복사한다.
- **컨트롤**: 사용자가 이름으로 부를 만한 버튼과 입력칸 전부를, 라벨과 호출되는
  핸들러를 함께 적는다. 예를 들어 `"Copy"` → `copyHeader`이다. "복사 버튼 눌러도 아무 일이
  없어요"는 가장 흔한 제보 중 하나인데, 항목에 문구만 있고 그 뒤의 컨트롤이 없으면
  답할 수 없다. 라벨에도 UI 문구처럼 사용자가 보는 번역을 붙인다.
- **화면 위치**: 사용자가 손가락으로 가리킬 영역, 예: "좌측 사이드바", "입금 폼
  상단", "설정 → 알림".
- **사용자 별칭**: 사람들이 실제로 부르는 말. 구어 표현, `입금` /
  `deposit` 같은 다른 언어, `충전`, `송금 메모` 같은 유의어, 흔한 오타. 별칭은 추정이므로 그렇게
  표시한다. grep 대상이 아니라 매칭 대상이다.

별칭 하나가 여러 기능에 맞으면 전부에 남기고, 별칭 인덱스에 `(ambiguous)` 로
충돌을 표시한다. 조회 단계는 아무거나 하나 고르지 말고 묻거나 둘 다 확인해야 한다.
진짜 충돌만 센다. 그 기능을 쓰는 사용자가 실제로 그 말을 할 때만 그 기능의 별칭이다.
인덱스를 다 쓴 뒤, 서로 다른 행에 같거나 거의 같은 말, 예: "한글 깨짐" / "한글 입력"이
있는지 훑어서 하나의 `(ambiguous)` 행으로 합친다.

있을 법한데 없는 기능도 적는다. 제품에 없는 것을 사용자가 찾을 가능성이 높으면,
예를 들어 복사 버튼이 없는 화면에서 복사 버튼을 찾는 경우, 별칭 인덱스에
`→ 없음; 가장 가까운 기능: <feature-id>` 행을 넣고, 비슷한 것조차 없으면
`가장 가까운 기능` 은 뺀다. 화면끼리 비교해서 찾는다. 다른 화면에는 있는
복사, 다운로드, 지우기 같은 공통 컨트롤이 한 화면에만 없으면 그 화면 한정 행을 넣는다:
`JSON 편집에서 복사 → 없음; 가장 가까운 기능: <feature-id>`. 이게 없으면 조회하는 쪽이
존재하지 않는 컨트롤을 찾아 그 화면의 항목을 하나씩 다 열게 된다.

### 5. 함정은 근거가 있을 때만 적는다

함정은 해당 기능의 알려진 실패 지점이다. 한글 입력을 삼키는 IME 조합 처리,
마지막 키 입력을 버리는 debounce, 오래된 잔액을 보여주는 캐시 같은 것. **증상 →
원인** 형태로 쓴다. 예: "셀에 한글을 치면 마지막 글자가 사라짐 → IME 조합이 끝나기 전에
Enter를 처리". 증상으로 표현할 수 없는 사실, 예를 들어 "렌더는 300ms 디바운스"는 동작
설명이지 함정이 아니다. 근거는 둘 중 하나를 인용한다.

- **과거 수정 이력**: 커밋 제목으로 후보를 찾고, 하나씩 열어서 확인한다. 제목이
  맞는다고 아직 근거는 아니다:

  ```bash
  git log --no-merges --format='%h %s' -- "<file>" ... \
    | grep -iE '^[0-9a-f]+ (revert|(fix|hotfix)[(!: ])|버그|오류' | head -10
  git show --stat <sha>     # 이 기능의 실패를 실제로 고친 커밋인지 확인
  ```

  이 필터는 빠짐없이 잡는 쪽을 택한다. 제목 맨 앞의 타입, 예를 들어 `fix:`, `Fix x`, git이
  만드는 `Revert "…"`이나 제목 어디든 있는 한국어 버그 단어를 잡는다. 정확도는 `git show`
  가 맡는다. 본문이 아니라 제목으로 거른다. `--grep` 은 메시지 전체를 검색하는데,
  한국어 이력에서는 거의 모든 본문에 `수정` 이 들어간다. 기능의 파일을 반드시 명시해서
  넘긴다. 목록이 비면 저장소 전체를 검색한다.
- **코드 자체**: 주석, 방어 로직, 또는 그 동작을 만드는 구문을 `path` → `symbol`
  로 인용한다. 원인이 되는 구문을 가리킨다. 앱을 실행해 봐야 확인되는 동작은 아직
  함정이 아니다.

근거가 없으면 함정도 없다. 지어낸 함정은 문서의 권위를 등에 업고 다음 디버거를
엉뚱한 길로 보낸다.

### 6. 검증하고, 연결한다

보고 전에 아래 네 가지 검사를 돌리고, 이어지는 점검 항목을 확인한다. `SRC` 에는
코드나 locale 카탈로그가 있는 루트를 전부 넣는다. 예: `src`, `public/locales`.
검사 대상 문구가 들어 있는 `docs/` 는 절대 넣지 않는다:

```bash
MAP="docs/FEATURES.md $(ls docs/features/*.md 2>/dev/null)"; SRC="src"

# 경로가 전부 존재하는지 — 저장소 루트 기준, `/` 포함. `/` 로 시작하는 라우트 URL은 제외
grep -ohE '`[^`/ ][^` ]*/[^` ]*\.[A-Za-z0-9]{1,5}`' $MAP | tr -d '`' | sort -u \
  | while read -r p; do test -e "$p" || echo "MISSING $p"; done

# 실제 UI 문구와 컨트롤 라벨이 전부 소스에서 grep되는지
grep -hE '^- \*\*(UI strings|Controls|UI 문구|컨트롤)\*\*' $MAP | grep -oE '"[^"]+"' | tr -d '"' | sort -u \
  | while IFS= read -r s; do grep -rqF -- "$s" $SRC || echo "MISSING-STRING $s"; done

# 인용한 심볼이 해당 파일에 있는지 — `path` → `symbol` 형식
grep -ohE '`[^`/ ][^` ]*/[^` ]*\.[A-Za-z0-9]{1,5}` → `[A-Za-z_$][A-Za-z0-9_$]*`' $MAP | tr -d '`' | sort -u \
  | while read -r p _ sym; do grep -qF -- "$sym" "$p" 2>/dev/null || echo "MISSING-SYMBOL $p → $sym"; done

# 함정마다 원인이 있는지, `근거:` 앞에 `증상 → 원인`
grep -hE '^- \*\*(Pitfalls|함정)\*\*:' $MAP | grep -vE ': none$|: [^→]+ → .+, (source|근거): ' | sed 's/^/NO-CAUSE /'
```

- 안 걸리는 문구는 바꿔 쓴 것이거나 낡은 것이다. 남겨두지 말고 고친다.
- 경로는 저장소 루트부터 전부 적는다. 줄여 쓴 경로는 검사에서 걸린다.
- 항목의 함정에 나오는 사용자 용어, 예: "정렬", "복사"는 별칭 인덱스에서 그 항목을
  가리키는 행에 있어야 한다. 없으면 그 함정은 정작 그 증상의 제보에서 닿을 수 없다.
- 기능마다 테스트 경로가 최소 하나 있거나, `테스트: none` 을 명시한다. 저장소에
  테스트가 아예 없으면 `전제` 줄에 한 번만 적는다. 비어 있다는 사실 자체가 정보다.
- `docs/FEATURES.md` 헤더에 `Verified at <sha> · <YYYY-MM-DD>`를 기록한다. SHA는 **이곳 한 군데에만** 둔다. `docs/features/` 의
  항목 파일에는 넣지 않는다. SHA가 두 곳에 있으면 서로 어긋나고, 갱신 모드는
  어느 쪽을 믿어야 할지 알 수 없다.

그다음 제보가 들어왔을 때 AI가 맵을 찾게 만든다. 프로젝트 루트 `CLAUDE.md`의
디버깅 관련 섹션에 한 줄 포인터를 추가하고, 파일이 없으면 그 한 줄로 새로 만든다.
`AGENTS.md`가 있으면 같은 줄을 거기에도 넣는다. 갱신 시에는 줄을 유지하고, 맵
위치가 바뀐 경우에만 고친다. 변경 사항은 응답에서 알린다:

```markdown
- "사이드바의 X가 안 돼요" 같은 모호한 버그 제보? 코드를 검색하기 전에 `docs/FEATURES.md` 에서 먼저 찾는다.
```

맵 작성은 콘텐츠 변경이므로 `CLAUDE.md` 의 작업 후 리뷰 게이트가 적용된다.

## 갱신 모드

기록된 SHA에서 diff를 뜬다: `git diff --name-status -M <sha>..HEAD`.

- diff에 파일이 걸린 항목은 의심 대상이므로 다시 검증한다. `R`로 표시된 이름이 바뀐 파일은
  경로를 고쳐 잇고, `D`로 표시된 파일이 모두 삭제된 항목은 지우며, 새로 생긴 라우트·화면·UI
  문구는 새 항목이 된다.
- 여전히 검증을 통과하는 항목은 다시 쓰지 않는다. 맞는 항목을 다시 쓰면 리뷰
  노이즈만 는다.
- **diff가 넓을 때**, 즉 대부분의 항목이 의심 대상일 때: 6단계 검사를 맵 전체에 돌리고,
  함정 근거는 인용한 파일이나 커밋이 diff에 있는 것만 다시 연다. 아래가 바뀌지 않은
  함정까지 전부 다시 읽는 건 발견 없이 비용만 든다.
- **기록된 SHA에 도달할 수 없음**, 예를 들어 rebase나 shallow clone 뒤: 그 사실을 알리고 모든
  항목을 재검증한다. 말없이 새로 만들어 덮어쓰지 않는다.
- 추가·변경·삭제된 항목을 보고하고, 헤더 SHA를 HEAD로 옮긴다.

## 문서 템플릿

`assets/feature-map-template.md`를 쓴다. 맵의 산문은 프로젝트 문서가 쓰는 언어로
쓰고, 템플릿의 제목과 필드 라벨은 영어로 둔다. 6단계 검사가 그 라벨을 grep하기
때문이다. 예전에 `검증 시점` 같은 한국어 라벨로 쓴 맵도 검사가 둘 다 받으므로
그대로 검증된다. 섹션 순서를 지킨다. 헤더에는 SHA와
선택 사항인 `전제`·`참고` 줄을 담고, 그다음은 AI가 가장 먼저 읽는 조회 절차, 그다음 두
인덱스, 그다음 항목. 헤더와 조회 절차 사이에는 아무것도 넣지 않는다.

**크기**: 한 파일이 ~500줄을 넘으면 `docs/FEATURES.md` 에는 헤더, 조회 절차, 두
인덱스, 기능 목록인 `ID | 목적 | 파일`만 남기고, 항목은 `docs/features/<화면>.md`
로 옮기되 **화면 또는 라우트당 파일 하나**에 그 화면의 항목을 모두 담는다.
기준은 기능 개수가 아니라 줄 수다. 관리하려는 비용은 조회할 때 읽어야 하는
분량이기 때문이다. 화면 단위로 묶는 이유는 제보가 화면을 가리키고 그 화면의 항목을
함께 읽게 되기 때문이다. 기능마다 파일을 나누면 15줄짜리 파일이 수십 개 생기고
조회할 때마다 한 번씩 더 연다. 인덱스는 조회 때 통째로 훑기 때문에 한 파일에 둔다.

## 작성 규칙

- **ID는 안정적인 kebab-case**로, 예: `deposit-memo`. UI 라벨이 바뀌어도 인덱스와 다른
  문서가 같은 ID로 참조할 수 있게 한다.
- **설명 말고 경로**: "메모 입력 컴포넌트"보다 `src/features/deposit/MemoInput.tsx`.
- **코드 경로는 단계당 한 줄**: 단순 전달만 하는 단계는 건너뛴다.
- **줄 번호 금지**: 수정할 때마다 흔들리고 아무도 다시 확인하지 않는다. 큰
  파일이면 대신 심볼 이름을 적는다. 예: `src/features/deposit/MemoInput.tsx` → `handleCompositionEnd`.
- **모르는 건 모른다고**: `테스트: none`, `함정: none` 은 정직하다. 추측한 값은 아니다.
