# Git 충돌 해결

merge나 rebase 충돌을 조사하거나 해결할 때 이 스킬을 사용한다. 충돌이 생긴 체크아웃의 루트에서 아래 명령을 실행한다. 조사 요청에는 진행 중인 작업과 양쪽 변경을 보고하고 편집 전 단계에서 멈춘다. 해결 범위 밖에 있는 작업 트리와 인덱스의 기존 변경을 보존한다.

## 진행 중인 작업과 양쪽 변경 확인하기

1. `git status`를 읽고 `git diff --name-only --diff-filter=U`로 해결하지 않은 경로를 찾는다. 이미 스테이징됐거나 수정됐거나 추적되지 않는 경로를 확인한다. 진행 중인 merge나 rebase가 없으면 Git 상태를 알리고, 시작할 작업을 확인한 뒤 진행한다.
2. 체크아웃 루트 기준의 정확한 경로로 병합되지 않은 인덱스 항목을 확인한다. 존재하는 단계의 내용을 `git show`로 읽는다. 파일 이름이 바뀐 경우 이전 이름과 새 이름의 항목을 확인한다. 해당 버전에 그 경로의 파일이 없으면 인덱스 단계도 없을 수 있다.

   ```bash
   git --literal-pathspecs ls-files -u -- "$conflict_path"
   git show ":1:$conflict_path"
   git show ":2:$conflict_path"
   git show ":3:$conflict_path"
   ```

   | 작업 | 단계 1 | 단계 2 | 단계 3 |
   |---|---|---|---|
   | Merge | 기준 버전 | `HEAD` | `MERGE_HEAD`에서 들어오는 버전 |
   | Rebase | 현재 재적용의 기준 버전 | 이미 재적용한 변경을 포함한 `HEAD` | 재적용 중인 변경의 버전 |

3. 관련 diff와 커밋 메시지를 읽고 양쪽이 바꾼 이유를 파악한다. rebase 중에는 `git rebase --show-current-patch`로 진행 중인 패치를 확인한다. 인덱스 단계와 커밋 이력으로 Git이 비교한 두 버전과 사용자가 충돌 파일에 이미 적용한 편집을 구분한다.

## 해결하고 대상 경로만 스테이징하기

1. 함께 유지할 수 있는 양쪽 동작을 모두 보존한다. 한쪽에서 코드를 옮기고 다른 쪽에서 수정했다면 새 위치에 수정을 적용한다. 삭제 또는 바이너리 충돌은 이력과 호출처를 근거로 결과에 남길 버전을 판단한다. 서로 양립할 수 없는 동작 중 무엇을 선택할지 근거로 판단하기 어려우면 사용자에게 확인한다.

   Markdown에서는 서로 독립적인 섹션과 목록 항목을 의도한 계층에 유지한다. frontmatter 키는 하나씩만 두고 스키마가 허용하는 경우에만 목록 값을 합친다. 본문, 상태, 날짜가 엇갈리면 문서의 의도와 저장소 규약을 근거로 결정한다. 두 근거로 의미를 판단하기 어려우면 사용자에게 확인한다.

2. 스테이징하기 전에 편집 결과를 양쪽 버전과 대조한다. 의도한 삭제나 이름 변경을 포함해 해결한 경로만 스테이징한다. 파일 이름이 패턴으로 해석되지 않도록 정확한 경로를 `git --literal-pathspecs add --`에 전달한다.

## 작업을 계속하기 전에 검증하기

1. `git diff --name-only --diff-filter=U`로 저장소 전체에서 미해결 경로를 확인한다. 이 목록이 비어 있어야 작업을 계속할 수 있다. 해결한 경로의 스테이징 결과를 읽고 각 경로를 `git --literal-pathspecs diff --cached --check -- "$resolved_path"`로 확인한다. 이름 변경은 이전 경로와 새 경로를 모두 검사한다. 스테이징한 내용에 충돌 마커가 남았는지 살피고 양쪽이 보존하려던 동작과 대조한다. Markdown에서는 frontmatter의 유효성, 섹션과 목록의 구조, 영향받은 링크도 확인한다.
2. 영향을 받는 동작을 확인하는 프로젝트 검사를 실행한다. 실패한 검사와 실행할 수 없었던 검사를 알리고 검증한 결과와 구분한다.
3. 해결한 내용, 양립할 수 없는 변경 중 하나를 고른 경우 그 선택, 작업을 계속할 수 있는 상태인지 알린다. 충돌 해결 요청은 검증한 해결 결과를 스테이징하는 단계까지 진행한다. 사용자가 계속, 중단, 건너뛰기를 승인한 경우에만 해당 작업을 실행한다. Merge를 계속하면 커밋이 생길 수 있고, rebase를 계속하면 커밋이 다시 작성될 수 있다. Rebase가 다시 멈추면 다음 충돌을 조사하고 검증한 뒤 계속한다.
