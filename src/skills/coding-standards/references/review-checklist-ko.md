# Review Checklist

> `coding-standards` skill의 참조 문서. SOLID, Clean Code, Functionality,
> Consistency + security/testing/performance를 강조한다.

SOLID, Clean Code, 기능, 일관성을 동등하게 검토한다. 각 발견은 변경이 어긴 계약과 실제 영향을 기준으로 등급을 매긴다.

## 심각도 범례

작성자가 머지 차단 사유와 후속 작업 가능 사유를 알 수 있도록 모든 발견에 아래 라벨 중 하나를 태그한다.

- **Blocker**. 잘못된 결과, 보안 결함, 데이터 경합, 호환성 계약 파기, 예외가 승인되지 않은 하드 한도 초과처럼 머지 전에 해결해야 하는 결함.
- **Major**. 변경한 코드에서 재현 가능한 유지보수 문제나 중요한 검증 누락. 영향과 필요한 수정을 적는다.
- **Minor**. 후속 작업이 가능한 개선. 명명이나 문서 개선의 이점을 구체적으로 적는다.

심각도가 불확실하면 확인된 영향과 추가로 검증할 조건을 구분한다.

## 코드 품질

### 크기 한도

프로젝트 한도와 예외를 확인한 뒤, 별도 규칙이 없는 항목에 아래 기본값을 적용한다. [크기 기준](code-thresholds-ko.md)
- [ ] File size ≤ 300 LOC soft / ≤ 500 LOC hard
- [ ] Function size ≤ 50 LOC soft / ≤ 80 LOC hard
- [ ] Parameters ≤ 5 soft / ≤ 7 hard
- [ ] Cyclomatic complexity ≤ 10 soft / ≤ 15 hard
- [ ] Nesting depth ≤ 4 soft / ≤ 6 hard
- [ ] hard 한도 초과 시 분할/리팩토링; soft 초과 시 논의

### SOLID Principles
- [ ] **S**ingle Responsibility: 각 module/class/function은 정확히 한 가지 이유로 변경된다
- [ ] 외부 구현을 독립적으로 추가하기로 한 경계에서는 기존 호출자가 그대로 동작한다. 도메인이 소유하는 닫힌 변형 집합에 경우를 추가하면 기존 분기를 함께 검토한다.
- [ ] **L**iskov Substitution: 서브타입은 슈퍼타입의 계약을 지키며, 예상치 못한 오버라이드가 없다
- [ ] **I**nterface Segregation: 호출자는 절대 사용하지 않는 메서드에 의존하지 않는다
- [ ] **D**ependency Inversion: 상위 모듈은 구체 구현이 아닌 trait이나 interface 같은 추상에 의존한다

### Clean Code
- [ ] 의도를 드러내는 이름; `data`, `tmp`, 인덱스 외 단일 문자 루프는 피한다
- [ ] 각 함수는 한 가지 일을 한 추상화 수준에서 수행한다
- [ ] I/O, 네트워크, 공유 상태 mutation 같은 side effect는 경계 레이어로 격리된다
- [ ] 깊은 중첩보다 guard clause 선호
- [ ] 상수 심볼화: 매직 넘버/문자열 없음, 하드코딩된 경로 없음
- [ ] Input → Processing → Return으로 구조화된 코드
- [ ] 코드가 곧 명세다: 코드가 이미 말하는 내용을 되풀이하는 주석 없음. 그런 주석은 이름 변경이나 추출 같은 리팩토링으로 대체되었고, 남은 주석은 *왜*만 담는다
- [ ] 주석이 두괄식으로 요점 한 문장 → 왜 순서이고, 비자명한 의도를 설명하며, 현재 동작과 일치한다
- [ ] 과잉 주석 없음: 의미 없거나 과도한 주석은 잡음으로 지적한다. 주석 밀도는 품질이 아니다
- [ ] 주석이 자신이 설명하는 코드와 함께 이동했다: 추출/분리/이름 변경 후 엉뚱한 선언에 남은 doc 없고, 한 선언에 doc 블록이 두 개 쌓여 있지 않다
- [ ] diff hunk 밖의 주석도 여전히 성립한다: 이름이 바뀐 심볼과 변경된 동작이 호출부·모듈 헤더·형제 파일·문서에서 옛 상태로 설명되고 있지 않다
- [ ] 모든 *왜* 주석의 주장이 짚을 수 있는 코드 경로·설정·외부 근거에 기반한다. 근거 없는 이유는 그 위의 코드가 옳더라도 결함이다
- [ ] dead code 없음, 주석 처리된 블록 없음, 티켓 없는 `TODO` 없음

## 기능성 리뷰

- [ ] 요구사항을 end-to-end로 정확히 구현
- [ ] Edge case 처리됨: empty, null, max, concurrent, partial failure
- [ ] 에러 처리가 구체적이고 실행 가능; 컨텍스트를 삼키는 catch-all 없음
- [ ] 무관한 모듈에 의도하지 않은 side effect 없음
- [ ] 리팩토링 시 이전 버전 대비 동작 동등성 검증됨

### 셀프리뷰와 PR 리뷰의 실패 경로

코딩 후와 PR 리뷰에서 이 검수를 적용한다. CI와 정상 동작 테스트가 통과했어도 적용한다.

1. 바뀐 동작, 호출자, 성공에 필요한 가정을 찾는다. `tdd-workflow`의 실패 사례 설계 기준에 따라 관련 있고 도달 가능한 실패 시나리오를 고른다. 적용할 사례가 없으면 이유를 설명한다.
2. 선택한 실패가 발생하는 지점에서 실제 작업을 거쳐 호출자에게 전달될 때까지 추적한다. 오류 전달, 성공 표시, 저장 상태와 메모리 상태, 자원 정리, 약속한 복구를 확인한다. catch 블록만으로 올바른 실패 동작을 입증할 수 없다.
3. 관찰하거나 추적한 결과를 계약과 비교한다. 일부만 완료되면 약속한 원자성이나 항목별 처리 방침을 확인한다. 롤백이나 재시도 같은 요구사항을 지어내지 않는다. 실패 처리 방침이 정해지지 않았다면 결정할 사안으로 알린다.
4. 테스트나 재현 절차가 그 실패에 도달하고 약속한 결과와 실패 후 상태를 검증하는지 확인한다. mock의 실패, 빌드 통과, 커버리지 수치만으로는 근거가 충분하지 않다. 충분한 기존 테스트는 재사용하고 변경과 위험에 필요한 검사만 추가한다.
5. 확인된 결함, 테스트 누락, 미검증 위험을 구분한다. 결함 지적에는 도달 가능한 유발 조건, 코드 위치, 잘못된 결과, 판단 근거를 쓴다. 실행하지 않은 검사는 통과나 확인된 버그로 단정하지 말고 한계로 보고한다.

- [ ] 관련 실패 시나리오를 정상 동작과 함께 검수하고 근거나 명시적인 한계를 남겼다
- [ ] 계약에서 요구하는 상태 보존, 정리, 부분 완료 효과, 복구를 확인했다

## 동시성과 자원 관리

변경이 도입하거나 사용하는 작업과 자원을 따라간다.

- [ ] 작업을 시작한 쪽이 정상 완료, 취소, 종료 때 결과와 자원을 어떻게 회수하는지 확인한다.
- [ ] 채널, 파이프, 잠금을 사용하는 경로에서 송신자나 수신자가 먼저 종료되어도 대기가 끝나는지 확인한다.
- [ ] 상태를 바꿀 수 있는 소유자를 식별하고, 작업 사이에 공유하는 데이터는 프로젝트의 동기화 방식을 따른다.

## Rust 오류 처리

- [ ] 복구 가능한 오류는 호출자가 구분해야 하는 정보와 함께 전달한다.
- [ ] `unwrap`이나 `expect`를 사용한 곳에서 해당 불변 조건이 성립하는지 확인한다.
- [ ] 오류를 표시하거나 기록하는 경계에서 진단에 필요한 맥락을 보존하고 자격 증명을 제외한다.

## 일관성 리뷰

- [ ] 프로젝트 코딩 컨벤션 준수: naming, formatting, error pattern
- [ ] 인접 코드와 동일한 솔루션 패턴 사용; 한 문제에 두 가지 방식 없음
- [ ] 로깅 스타일, correlation ID, error 메시지 형태가 주변 모듈과 일치
- [ ] `snake_case` / `camelCase` / `PascalCase` 같은 naming convention이 언어 관용구와 프로젝트 표준에 부합
- [ ] API / response 형태가 기존 스키마와 일치; 임시 필드 없음
- [ ] 의존성 추가가 기존 스택에 부합; 같은 일을 하는 중복 라이브러리 없음
- [ ] 문서 톤과 구조가 주변 문서와 일치

## 지원 플랫폼

프로젝트의 배포 설정과 문서에서 지원 환경을 확인한다. 변경된 동작이 환경에 따라 달라지는 경우 해당 환경에서 계약을 검증한다.

- [ ] 파일 경로는 호출자가 사용할 형식에 맞게 구성한다. 심볼릭 링크나 대소문자가 경로의 의미를 바꾸는 경우에는 실제 경로로 검사한다.
- [ ] 프로세스를 실행할 때 실행 파일과 각 인자의 경계를 유지한다. 공백이 있는 경로나 빈 인자가 지원 대상이면 자식 프로세스가 받은 값을 확인한다.
- [ ] 실행 권한과 줄바꿈을 변환하는 코드는 배포물의 형식과 파일 비교 규칙을 따른다.

## 보안 리뷰

- [ ] 코드에 시크릿 없음
- [ ] 입력 검증 및 정제됨
- [ ] SQL injection 취약점 없음
- [ ] XSS 취약점 없음
- [ ] 인증/인가 적용됨
- [ ] 전체 체크리스트는 `security-review` skill 참고

## 테스트 리뷰

- [ ] 신규 코드에 테스트 있음
- [ ] 버그 수정에 회귀 테스트 있음
- [ ] 테스트가 결정적임
- [ ] E2E에 success path와 failure path 있음
- [ ] 전체 체크리스트는 `tdd-workflow` skill 참고

## 성능 리뷰

- [ ] 명백한 성능 이슈 없음
- [ ] 데이터베이스 쿼리 최적화됨
- [ ] N+1 query 문제 없음
- [ ] 적절한 캐싱 고려됨

## 문서 리뷰

- [ ] 복잡한 로직이 문서화됨
- [ ] API 변경이 문서화됨
- [ ] 필요시 README 업데이트됨
- [ ] Breaking change 명시됨

## 리뷰어 액션

1. **Read**: 컨텍스트와 목적 이해
2. **Verify**: 요구사항 대비 점검
3. **Test**: 필요시 로컬에서 테스트 실행
4. **Comment**: 건설적 피드백 제공
5. **Approve/Request Changes**: 명확한 결정
