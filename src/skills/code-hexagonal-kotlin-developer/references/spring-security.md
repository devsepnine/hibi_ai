# Spring Security for MVC and WebFlux

Find the HTTP stack that actually serves the route and read its existing security configuration. Use `HttpSecurity` and `SecurityFilterChain` for servlet MVC. Use `ServerHttpSecurity` and `SecurityWebFilterChain` for WebFlux. When several chains exist, check their matchers and order. Confirm which chain handles each changed route and how unmatched routes are handled. See the official guides for [servlet configuration](https://docs.spring.io/spring-security/reference/servlet/configuration/java.html) and [WebFlux configuration](https://docs.spring.io/spring-security/reference/reactive/configuration/webflux.html).

Derive access rules from the API contract. Check the credential transport before changing CSRF settings, including cookies and other credentials that a browser attaches automatically. If the application serves cross-origin browser requests, check the applicable CORS configuration and handle preflight before authentication. Inspect response headers at the boundary that serves the client, including the proxy when it adds or replaces them. See the Spring Security guides for [CSRF](https://docs.spring.io/spring-security/reference/features/exploits/csrf.html), [servlet CORS](https://docs.spring.io/spring-security/reference/servlet/integrations/cors.html), and [reactive CORS](https://docs.spring.io/spring-security/reference/reactive/integrations/cors.html).

Validate the request shape at the HTTP boundary and apply business invariants in the domain or use case. Keep HTTP response mapping in the adapter. Verify the real security chain with `MockMvc` or `WebTestClient` and the appropriate security test setup. Cover allowed access and the authentication or authorization failures relevant to the route. Include CORS and CSRF cases when the change affects these policies.
